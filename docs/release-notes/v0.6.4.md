# Release v0.6.4 - Meru refuses Ollama's cloud models

**November 2026**

Ollama can run some models on ollama.com and answer for them through the local
API, which would send every prompt off your machine. Meru now refuses those
models, both in `config.toml` and before each request.

---

## Upgrading from v0.6.3

### Breaking changes

One, and only for a config that names one of Ollama's cloud models. If
`[models]` or a model set names a model whose tag is `cloud` or ends in
`-cloud`, such as `gpt-oss:120b-cloud`, `merud` won't start, and its log names
the key:

```text
models.main: "gpt-oss:120b-cloud" is an Ollama cloud model, which runs on ollama.com and would send every prompt off this machine…
```

Put a local model in that key and start `merud` again. A config with only local
models loads as before. The socket protocol, `meru.db` and the transcripts don't
change.

### New config keys

None.

### Upgrade instructions

**The one-line installer on a Mac.** Run it again; it keeps your config.toml:

```sh
curl -fsSL https://github.com/aarora79/meru/releases/latest/download/install.sh | bash
```

**The Mac installer.** [Download the disk image](https://github.com/aarora79/meru/releases/latest/download/Meru-macos-arm64.dmg),
open it, and run "Install Meru.app". It leaves your config and memories alone.

**Linux.** Run `install-linux.sh` again; it keeps your config.toml:

```sh
curl -fsSL https://github.com/aarora79/meru/releases/latest/download/install-linux.sh | bash
```

**From source.**

```sh
cd meru
git pull origin main
git checkout v0.6.4
go install ./cmd/merud ./cmd/meru
launchctl kickstart -k gui/$(id -u)/com.meru.merud   # Linux: systemctl --user restart merud
```

Then, on a Mac that reads Apple Notes: macOS drops the Full Disk Access grant
when the `merud` binary changes. In System Settings, open Privacy & Security,
Full Disk Access, and turn `merud` off and on again.

## Major features

### Ollama's cloud models stay off

Once you sign in to ollama.com, Ollama lists cloud models beside your local
ones and answers for them on `127.0.0.1:11434`, while it passes the whole
prompt to ollama.com. Meru's rule that model traffic goes only to Ollama on
loopback couldn't see that. Now:

- `config.toml` refuses a model tagged `cloud` or ending in `-cloud`, in
  `[models]` and in every model set.
- Before each request, the engine checks the model again. It refuses a cloud
  tag, and a model whose details from Ollama name a remote host, which catches
  a cloud model copied to a plain name. No request goes out.
- The check costs one lookup per model per run, and `merud` makes most of them
  at startup anyway.
